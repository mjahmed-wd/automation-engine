22. DOM injection via evaluate evaluate

The evaluate action runs your expression in the page's main JS world via CDP Runtime.evaluate — same realm as the page's own inline <script> tags. Anything you can do in DevTools Console, you can do here: append elements, inject stylesheets, delete nodes, rewrite text, call the page's globals (Redux store, jQuery, framework hooks). The page can't tell whether the mutation came from its own scripts or from outside. This is the escape hatch for "make a one-off change while the automation runs" — for example dimming rows you've already processed in a CRM list, hiding noisy UI, or surfacing a custom progress badge.

Multi-statement code needs an IIFE because Runtime.evaluate runs in script mode and doesn't return the last expression — write (() => { …; return value; })(). Return values get JSON-serialized, so primitives and plain objects survive into ctx.outputs via saveAs; DOM nodes come back as {}. Mutations persist until the next navigation or reload.

The fix is to scope the option search to the FIRST select__menu-list — react-select only renders that container while the menu is open, so by the time waitFor sees one, it's the one we just opened. Real-world demonstration of the "scope xpath to the open container" pattern.

R4. Shepherd — pay one invoice (closed shadow) pierceClosed + data-test-id anchoring

Shepherd renders its UI inside a closed shadow root — invisible to the fast-path document.evaluate. The engine auto-detects closed shadow at attach and routes to CDP, but you can also force it with pierceClosed: true for clarity. This script also demonstrates the data-test-id anchoring pattern: text-based xpath would be fragile against Vue's text-wrapping and framework re-renders, but [@data-test-id='row-0'] is stable. Multi-step: fill, wait for the framework to settle, then click. Requires being logged into the Shepherd app first — the script doesn't include a goto.
